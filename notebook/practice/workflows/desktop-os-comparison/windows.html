版本区别

桌面版以 Windows 11（x64）为准，Server 以 2025 为准。

版本 功能差异 支持周期 硬件与授权
Home 基本桌面、WSL 2、Dev Drive；有条件支持设备加密 每个发布版本 24 个月 常规 Windows 11 硬件要求；OEM、零售
Pro Home ＋ Hyper-V、Sandbox、Windows Containers、完整 BitLocker、RDP 主机、AD / Entra 加入、组策略与更新策略 同 Home 同 Home；另有组织授权
Enterprise Pro ＋ 组织级安全、部署与管理能力 每个发布版本 36 个月 同 Home 的硬件要求；组织授权
Enterprise LTSC 2024 Enterprise 的桌面与管理能力；固定于 24H2，持续接收安全与质量更新；Store 及部分应用、工具支持受限 5 年，至 2029 年 同 Enterprise 的硬件要求；企业批量授权
IoT Enterprise LTSC 2024 同 Enterprise LTSC 2024；面向固定用途设备 10 年，至 2034 年 可选最低配置：2 GB 内存、16 GB 存储、BIOS，TPM 与 Secure Boot 可选；固定用途设备的 OEM 或批量授权
Server Standard AD DS 域控制器、DHCP / DNS、文件服务、IIS、Hyper-V、RDS 10 年，至 2034 年 按核心授权；整机足额授权含 2 个 Windows Server 虚拟环境，可叠加
Server Datacenter Standard ＋ Storage Spaces Direct、Network Controller 同 Standard 同 Standard；虚拟环境数量不限
Server Datacenter: Azure Edition Datacenter 的主要能力 ＋ Azure 激活与平台集成，另有年度产品更新 同 Standard 仅 Azure / Azure Local 虚拟机；按平台授权

Server 的虚拟环境权益以物理系统仅承载与管理虚拟机为前提；按虚拟机或用量授权另有规则。RDS 多用户桌面与 RemoteApp 另需 RDS CAL。

Server 安装选项：Core 无完整桌面，Desktop Experience 带图形界面；互换需重装。LTSC 的应用与驱动支持期由厂商决定。

包管理与软件分发

Windows 没有像多数 Linux 发行版那样，由同一个仓库和包管理器统一维护系统与大部分应用。系统组件由 Windows Update 维护，应用则由厂商安装包、Store 或第三方包管理工具分发；装了包管理器也不意味着应用的更新全部归它管理。

  • WinGet：微软工具，App Installer 提供；用清单调用 EXE / MSI / MSIX 等安装包，支持安装、升级、卸载和清单导入 / 导出。安装范围与提权由具体包决定。
  • Scoop：偏命令行与便携工具，默认装到用户目录，shim 提供命令入口；JSON manifest + bucket 管理下载和依赖。
  • Chocolatey：包 + PowerShell 脚本自动化，适合传统软件与组织内部仓库。

这些工具管理的安装包也有不同的部署模型：

  • MSI / EXE：MSI 有标准安装、修复和卸载机制；EXE 由厂商定义。更新多由应用或包管理工具负责。
  • MSIX / AppX：系统管理部署、包身份和卸载；桌面应用可为 full trust 或 AppContainer，打包本身不保证沙箱隔离。
  • Store：分发渠道，可承载不同应用类型；更新方式取决于打包方式。
  • 便携软件：解压运行、替换升级；配置仍可能写入 AppData 或注册表。

与 Linux 的共享库依赖管理相比，Windows 桌面应用常自带依赖，或要求另装 VC++ 等运行库，多种版本可以共存。WinGet 主要自动化已有安装流程，并不把整个系统转换成统一的依赖树。

发布模型

通道 功能更新 安全与质量更新
GA 通常年度更新，部分新功能分批推出 月度累计补丁
LTSC 固定功能基线 月度累计补丁
Insider 按预览通道提前发布 随预览构建更新

Home 可暂停更新、调整重启；Pro / Education / Enterprise 还可通过组策略或 MDM控制更新类型、延迟与部署节奏。

虚拟化与容器

Windows 原生应用接口与 Linux 不同，普通 Linux ELF 程序不能直接作为 Windows 应用运行。WSL 2 通过运行 Linux 内核提供 Linux 环境；Windows Containers 则运行 Windows 用户空间，两者的容器镜像不能互换。

  • WSL 2：Virtual Machine Platform（Hyper-V 子集）+ 轻量虚拟机 + 完整 Linux 内核，Home 可用。Linux 容器需另装 Docker 等运行时。
  • Hyper-V：Type-1 hypervisor，Pro / Enterprise / Education 提供完整虚拟机工具。VBS / HVCI 等共享 Windows hypervisor，无需先安装完整 Hyper-V 功能。
  • Sandbox：一次性隔离桌面，关闭清空，Pro / Enterprise / Education 可用。
  • Windows Containers：Process isolation 共享宿主内核，受版本兼容约束；Hyper-V isolation 使用独立内核。Win11 Pro / Enterprise 默认后者，面向开发测试。

服务、配置与日志

Windows 的这些职责分散在几个系统组件中，没有一个与 systemd 完全对应的管理入口：

职责 Windows 中的主要机制 与常见 Linux 环境的对应关系
后台服务 Service Control Manager（SCM），通过 services.msc、sc.exe 或 PowerShell 管理 类似 service unit 的启动、停止、依赖和故障恢复；不承担全部启动流程
定时与触发任务 Task Scheduler（任务计划程序） 类似 cron / systemd timer，也支持登录、事件等触发条件
结构化系统日志 Windows Event Log（事件日志），通过 Event Viewer 查看 类似 journal 的一部分用途；应用也可能另写日志文件
系统与应用配置 Registry（注册表）、配置文件、组策略 配置分散在多种存储中，不统一放在 /etc；组策略用于施加管理规则

注册表按键组织配置，HKLM 主要保存机器级设置，HKCU 保存当前用户设置。应用文件通常在 Program Files，机器共享数据在 ProgramData，用户配置和缓存常在 %APPDATA% / %LOCALAPPDATA%。备份应用环境时，只复制程序目录往往不够。

PowerShell 是常用管理入口，管道主要传递对象，服务、进程和事件日志等可通过 cmdlet 查询；它不是系统的服务管理器本身。

文件系统与权限

  • 卷与路径：常见路径以 C: 等盘符开头，也可将卷挂载到目录。默认通常保留文件名大小写、但按大小写不敏感方式查找；涉及 Linux 工具链时需要留意目录的大小写设置。
  • NTFS：常规系统卷使用的文件系统，支持日志、访问控制列表（ACL）、硬链接等。其日志主要用于崩溃后恢复文件系统一致性，不提供一般文件内容的端到端校验。
  • ReFS / Dev Drive：ReFS 不能作为启动卷；Dev Drive 面向源码、包缓存和构建产物。文件数据校验可选，发现损坏后的自动修复需要冗余副本。
  • 身份与 ACL：用户和组以 SID 标识，文件等对象的 ACL 决定访问权限，比 Unix 的 owner / group / other 模型更细。微软账户是登录方式之一，本地访问控制仍基于 Windows 身份与访问令牌。
  • UAC 与提权：管理员日常通常也使用受限令牌，执行管理操作时再提权。UAC 不等于应用沙箱；传统桌面应用通常可以访问当前用户有权访问的文件。
  • BitLocker：保护卷上的静态数据，作用类似 LUKS；解锁后，运行中的应用能否访问文件仍由权限和隔离机制决定。
