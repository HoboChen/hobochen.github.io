YA Hexo

Markdown 与 Jupyter

Markdown 和 Jupyter 应当是并列的一等公民：

  • Markdown 代表叙述、说明、整理后的内容
  • Jupyter 代表计算、实验、数据处理和可复现逻辑

很多知识不是纯文章，而是“文本解释 + 可运行过程”。理想情况下：

  • 静态模式下，可以用Pyodide
  • 有server的话可以连接真正的 Jupyter kernel

目录结构与分级发布

Hexo 的结构主要来自文件系统：目录、_posts、front-matter、permalink。这个模型简单，但内容结构和磁盘结构强绑定。

更好的做法是把网站结构抽象到一个独立的声明文件（如 structure.yaml）：

  • 显式定义树形结构
  • 显式控制页面顺序
  • 显示控制分级发布
    • 支持多个site
    • 每个site有对应的访问级别
    • 每个内容有对应的访问级别
    • \to 支持同一套内容源生成公开站、内网站、私人站

更好的设计

  • LCD / OLED / E Ink 都是重要场景
  • 背景 tint、字体、字号、行距、正文宽度可调
  • 支持双栏阅读、三栏布局、自动 TOC、键盘导航
  • PWA 和离线缓存

静态与动态

Hexo 最重要的优点应当保留：可以生成纯静态网站。静态模式适合公开发布、长期归档和低维护部署，放到 Nginx、S3、GitHub Pages、Cloudflare Pages 都可以。

理想情况下，如果有server的话：

  • 评论：围绕页面做讨论和批注；AI & Human Native
  • Quick Edit：浏览器里直接编辑 Markdown
  • 全站搜索
  • 真 Jupyter：连接服务器侧 kernel，而不只是浏览器 Pyodide

LLM <—> VM

LLM 通过 VM 接口直接操控任意操作系统的桌面环境。

控制通道

QEMU QMP (JSON over socket) 是最干净的方案，无需在 VM 内装任何东西：

  • 键盘：sendkey 支持任意按键/组合键
  • 鼠标：mouse_move + mouse_button
  • 截屏：screendump 导出 framebuffer 为图片

VirtualBox 也行：VBoxManage controlvm 提供 screenshotpng、keyboardputstring、keyboardputscancode。

感知通道

纯截图（QMP screendump）信息量低，可通过 VM 内轻量 agent 增强：

方案 需要 VM 内 agent 信息
截图 否 像素，依赖多模态视觉
Accessibility tree 是 UI 元素层级 + 坐标 + 语义，几 KB JSON
CDP (Chrome DevTools Protocol) 是 (Chrome flag) 完整 DOM tree
混合 是 截图 + a11y tree + 剪贴板 + 窗口列表

Accessibility tree 性价比最高：适用所有 GUI 应用，数据量小，token 消耗低。Linux 用 AT-SPI2，Windows 用 UI Automation，macOS 用 AXUIElement。

安全隔离架构

LLM agent 不可信（prompt injection 风险），不应裸跑在 host 上。

推荐方案 — 两个平级 VM（避免 nested virtualization 的性能损失）：

Host (不跑 agent 代码)
├── VM1: Agent (轻量 Linux, Python agent)
│   ├── 网络白名单：仅 LLM API + VM2 QMP
│   └── 无 host 文件系统访问
└── VM2: Controlled Guest (任意 OS)
    └── QMP socket 暴露给 VM1

或更轻量：容器 (Docker + seccomp/AppArmor) 跑 agent，QEMU VM 跑 guest。安全性对 agent 代码足够，真正需要强隔离的是 guest。

QMP 是单向控制协议，guest 无法反向攻击 agent 端。

现有项目

  • Anthropic Computer Use：Docker + Xvfb + xdotool，纯视觉驱动，仅 Linux 容器
  • E2B Desktop Sandbox：云端沙箱 VM，提供截屏和键鼠 API
  • UI-TARS (ByteDance)：accessibility tree + 截图双通道
  • OSWorld / WebArena：学术 benchmark，a11y tree 作为 observation

YA ds4.c

在 AMD / Intel 消费卡上跑 DeepSeek V4 Flash 284B。

模型与量化

V4-Flash：284B 总参数 MoE，每 token 激活 ~13B（256 routed experts 选 top-6 + 1 shared）。274B 是 routed experts，~10B 是 non-expert（attention/shared/router/norms）。

ds4.c（antirez）的 q2 非对称量化把 80.8 GiB GGUF 装进 96-128GB 机器：

组件 参数量 量化 占用
Routed expert up/gate ~182B IQ2_XXS (2.06 bpw) ~46.8 GiB
Routed expert down ~91B Q2_K (2.56 bpw) ~29.1 GiB
Attention/Shared/Output ~10B Q8_0 / F16 / F32 ~4.9 GiB
总计 284B 平均 ~2.3 bpw 80.8 GiB

q4（153.3 GiB）：routed experts 改用 Q4_K，其余不变。每 token 读取：~9.8 GiB non-expert + 6/256 × 71 GiB experts ≈ 11.5 GiB。

ds4.c 现状

Metal (macOS) + CUDA (Linux) 双后端，单 GPU。特制 GGUF、磁盘 KV cache（prefix 复用）、DSML tool call exact replay。dmlx 是另一条路线（Zig+MLX，expert streaming，48GB Mac 也能跑）。

多卡方案分析

两种并行策略：

TP=4 + EP=4（有 sync）：attention tensor parallel + expert parallel。每卡读取 ~2.87 GiB/token，但每层需 PCIe all-reduce。

纯 EP（no sync）：每卡存完整 non-expert 副本 + 1/N experts，MoE 层只传 hidden state（~7.4 MB/token，PCIe 5.0 ~0.23ms）。每卡读取 ~10.22 GiB/token。简单但上下文受限。

配置 总 VRAM q2 常驻 no-sync 短ctx tok/s 1M ctx 整机成本
M3 Max 128GB 128 统一 ✓ 27 (实测) ✓ ~$4k
M3 Ultra 512GB 512 统一 ✓ 37 (实测) ✓ ~$8k
2×R9700 32GB 64 GB ✗ streaming ~10-15 ✗ ~$5k
4×R9700 32GB 128 GB ✓ ~32-38 需TP ~$10.5k

经济性

V4-Flash API 极便宜，家用电费跑出来更贵（哪怕忽略硬件成本）。
